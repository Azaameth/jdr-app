# Research: Equipment Stat Effects

## D1 — Schema field name for the structured bonus

- **Decision**: `statBonus?: { stat: 'maxHp' | 'maxMana'; amount: number }` on `WeaponArmorItem`.
- **Rationale**: confirmed with the project owner during plan-phase discovery (decision `01KY2NN81QKVGFAE6F913JNYHE`). `statBonus` is unambiguous next to the item's existing own-combat-stat fields (`damageBonus`, `armorRating`) and next to `JetCalculator.vue`'s unrelated "manual modifier" concept, which spec.md's Domain Language table already flagged as a naming collision to avoid ("modifier" alone).
- **Alternatives considered**: `bonus` (spec.md's own prose default — rejected as too generic, risks collision with future non-stat bonuses); `effect` (rejected — implies a broader mechanic, like duration/conditional effects, than this mission's simple additive number).

## D2 — Where the aggregation logic lives

- **Decision**: a new pure function `computeEffectiveMaxStat(baseValue: number, items: WeaponArmorItem[], stat: 'maxHp' | 'maxMana'): number` in `src/utils/effectiveStats.ts`, not a Vue composable.
- **Rationale**: `src/components/vitruve/jetFormula.ts` is the direct precedent for "a formula the sheet needs" in this codebase — it is explicitly documented as "No Vue, no Firestore — this file must stay importable from a plain unit test with zero framework/runtime dependencies" (`jetFormula.ts:4-6`). NFR-002 requires the same property here ("covered by unit tests on the aggregation logic, independent of any Vue component"). C-005 permits either "composable/util" but a plain function is strictly simpler than a composable when there's no reactive state to own — the caller (a `computed()` in the Vue component) already provides reactivity.
- **Alternatives considered**: a `useEffectiveStats()` composable wrapping the same logic in `ref`/`computed` internally — rejected as unnecessary indirection; the existing `useInventoryStore` already owns the reactive `inventory`/`childInventories` refs, so the aggregation function only needs to be called from a `computed()` in each consuming component, exactly like `jetTotal()` is called today from `JetCalculator.vue`.

## D3 — Child inventory availability gap

- **Finding**: `useInventoryStore` (`src/controllers/useInventoryStore.ts:14`) holds a single module-scope `inventory = ref<CharacterInventory | null>(null)`. `PlayerView.vue:599` calls `inventoryStore.loadInventory(characterId.value, campaignId.value)` exactly once, for the *parent* character, in the same `Promise.all` that also fetches `listChildrenOf(...)`. No code path today loads a transformation/child's own `CharacterInventory` — `ChildSheetTab.vue` currently has no inventory awareness at all (it renders vitals from `childSession`, not from any inventory).
- **Decision**: extend `useInventoryStore` with a second cache, `childInventories = ref<Record<string, CharacterInventory>>({})`, populated by a new `loadChildInventories(childIds: string[], campaignId: string)` method that calls the existing `getInventoryByCharacterId` once per child ID in parallel. Call it from `PlayerView.vue` right after `listChildrenOf` resolves (same place the child list itself becomes known), not lazily per tab-switch — children.value is already fully loaded upfront (mirrors how `childSessions` are all present on the participant doc at once), so eager loading avoids adding tab-switch-triggered async loading state to a UI that doesn't have any today.
- **Rationale**: keeps `getInventoryByCharacterId` and the repository layer completely untouched (FR-005's requirement is only about *which* items count, not about adding new persistence). Keeps the existing singleton `inventory` ref's behavior byte-for-byte unchanged for the parent character, so the already-shipped backpack/weapons UI (`inventory-slots-dons-01KXRF5M`) has zero regression risk.
- **Alternatives considered**: reuse the single `inventory` ref and swap its contents on tab switch — rejected, because `BackpackGrid.vue`/`WeaponArmorList.vue` on the *parent* tab are still visible/editable while a child tab might be active in principle (tabs don't unmount the parent's own inventory-editing UI), so overwriting the one shared ref would corrupt the parent's own displayed/editable inventory the moment a child inventory loads. A keyed cache avoids this entirely.

## D4 — Interaction between `statBonus` and `damageBonus`/`armorRating`

- **Finding**: these are different concepts already coexisting on `WeaponArmorItem` — `damageBonus`/`armorRating` describe the item's own combat stat (used only for display today, per `MIGRATION_BACKLOG.md` item 4's own framing: "zero code paths reading them into a computation"), while `statBonus` is a wholly new mechanical effect on a *character* stat (max HP/Mana). Nothing in the current codebase links them.
- **Decision**: no interaction — both fields can be set independently and simultaneously on the same item (e.g. a shield with `armorRating: 4` display value *and* `statBonus: { stat: 'maxHp', amount: 4 }`); `computeEffectiveMaxStat` never reads `damageBonus`/`armorRating`.
- **Rationale**: this was flagged as an open assumption in spec.md but not raised as a discovery question — it resolves itself once the two fields' actual (non-)relationship in existing code is confirmed. No further user input needed (C-004 already locks `statNote` as separately untouched; this finding just extends the same "independent fields" pattern to `damageBonus`/`armorRating`).

## D5 — Clamping of current HP/Mana against the new effective max

- **Finding**: `VitruveSheet.vue:44,49,59` and `ChildSheetTab.vue:104-105` compute `+`/`-` button disabled-state by comparing the live `hp`/`mana` against `session.maxHp`/`session.maxMana` (the raw stored value) — e.g. `s.hp >= s.maxHp` disables the "+" button.
- **Decision**: these comparisons switch to compare against the *effective* max (the `computeEffectiveMaxStat` output), not the raw stored field, per spec.md's edge case: "existing clamping of current value to max continues to apply against the new equipment-adjusted max." This is in scope for IC-04/IC-05 (display work package), not a separate concern.
- **Rationale**: directly stated in spec.md's Edge Cases section; failing to update these comparisons would let current HP visually exceed the displayed max mana bar when equipment bonuses raise the effective max above the raw stored one.
